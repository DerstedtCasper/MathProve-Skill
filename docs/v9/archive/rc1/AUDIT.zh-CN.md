# CoMath / MathProve 设计审阅与 v9 改进报告

日期：2026-09-27（Australia/Brisbane）。交付版本：9.0.0-rc1。

## 结论与证据范围

**CoMath 的公开设计方向是正确的：把研究活动与最终证明权威分开，而不是让一组 agent 用共识给自己发证书。下一轮优化应主要减少无效搜索、重复上下文、集成冲突和人工操作负担，而不是继续增加人格数量或无限拉长单次推理。** 对非 Pi 用户，应将“研究规范一致”和“安全/证明权威等价”作为两个不同目标。

本次不能称为完整源码审计。容器中的 Git/网络下载失败；web 能读取仓库页面与部分 raw 文本，但核心实现路径未取回。实际覆盖如下：

| 对象 | 本次取得的材料 | 可做的判断 | 不可做的判断 |
|---|---|---|---|
| comath-pi-lab | 仓库根 README、公开目录与接口描述 | 架构设计、对外承诺、集成路线与待验收事项 | daemon/proof-kernel 实现是否满足承诺，真实权限绕过或竞态 |
| MathProve-Skill | 根 README、完整旧 `skill/SKILL.md` 文本 | 入口协议、文档中的证据表述、迁移方向 | v8 各模块真实行为、原测试是否通过、完整依赖兼容 |
| 两个仓库版本 | web 提供的缓存页面 | 页面所述设计 | 固定 HEAD、完整最近提交、可重现源码快照 |
| 本次新 v9 | 全部独立新增实现、测试与示例 | 本地测试覆盖内的行为 | 真实 Codex、Lean、Windows 与上游完整回归 |

因此，下文分为“观察到的设计/入口问题”“建议”“本包已实现”“尚未验证”四类。不能把建议伪装成已定位的上游代码缺陷。来源编号对应 `SOURCES.md`，机器可读覆盖见 `SOURCE-COVERAGE.json`。

## 1. CoMath 已经做对的事，不应重复发明

公开 README 已描述 Pi 薄宿主、`comathd` 状态写入边界、FormalSpecLock、AssumptionLedger、StatementDiffGate、no-cheat 检查、最终 Lean/mathlib 回放及相关哈希绑定，并区分宿主特权操作。也描述了 HTTP / in-process 使用面。[S01]

这些不是本报告“新发现应该加上”的功能。真正需要验收的是：所有到达最终状态的路径是否经过同一权威检查；历史通过在源码、依赖、目标语义、验证器版本或人工签核快照变化后是否失效；外部工具失败/超时/重试是否可能沿用旧绿色状态。未取回实现前，不能断言它存在这些漏洞。

公开版还说明未包含私有评测、测试夹具或 smoke QA。[S01] 这不等于“没有测试”，但对外部研究者而言缺少可独立执行的最小验收面。建议另发脱敏的 conformance suite：不暴露私有题库，只验证状态机、工具契约和拒绝错误的性质。

**建议的分层**：研究层负责问题、路线、引理和反例；宿主层负责工具权限、真实子代理和人工确认；证明层负责对锁定目标与环境的验证；展示层只能显示这些结果的投影。不要让 Pi UI 或非 Pi 的 Stop hook 成为另一条发证路线。

## 2. 顶尖团队经验：可移植的是工作机制，不是成绩数字

OpenAI 的早期科研案例强调专家定义问题、拆解、独立检查，也明确提到虚构引用、领域细节与无效路线等失败模式。[S04] 对工作台最实用的迁移是：启动时做领域热身和来源查验；在关键命题上让模型既尝试证明也尝试否证；结果的“新”必须由检索与人审另外确认。这些案例不是本包能直接照搬的平均提效比例。

2026-08-01 的 OpenAI 后续数学成果页面把论证生成、人工参与整理、Lean 形式化以及贡献归属分开叙述。[S12] 本报告仅依据该公开页面，不宣称复核其中各个数学结果或 Lean 证书。工程启示是为一次研究保留阶段产物和贡献记录，而不是把最终聊天总结写成唯一溯源。新增 interaction-card 模板用于记录实际模型/工具、人类修改、核验范围和不足。

Aletheia 的论文摘要描述了自然语言的生成、验证、修订循环，并讨论自主性、创新性及人机交互记录。[S05] 应借鉴循环和贡献透明度，但**自然语言 verifier 不是 Lean kernel**，更不是自动的新颖性裁决。可以让它更早发现问题、减少昂贵形式化回合；最后的形式检查仍另行执行。

Anthropic 的多代理工程经验支持清晰任务合同、按复杂度分配资源和让真正可并行的问题并行。[S06] 长运行 harness/context 经验支持初始化、增量工作、外部进展记录和分层取上下文。[S07, S08] 这些来自通用研究/软件工程系统；本报告不把其基准数字转写成数学系统的速度保证。

近期大学实验室公开材料还把形式化任务表达为任务依赖与编译调度问题。[S09；本次仅取得检索摘录] 本报告据此只提“可复用引理接口、依赖调度、搜索复用”的方向，不声称复现其系统或大型定理完成度。

## 3. 最高优先级：把长期持续研究改为可恢复的小工作单元

旧 `skill/SKILL.md` 对 hard/research 路径写入 `context_target_tokens>=1_000_000` 等长时运行要求。[S03] 这里观察到的是**入口目标/指令**，不是已经测量到每次实际花费百万 token。长期研究需要连续积累，但连续积累不等于每次携带全部历史。

建议以一个可验证问题作为最小单元：精确假设、目标接口、已知材料、允许工具、输出位置、预算、停止条件。一次任务可以失败，但必须留下失败在哪一步、反例条件和下一条有效信息。不要只留“继续努力”。

v9 已实现任务 DAG、claim/heartbeat/finish、原子并发上限、spec hash、独立 attempt 目录和内容引用。租约过期后的迟到结果不能直接接管新任务。默认 2 个并行租约、每任务 3 次尝试、总计 32 次，是可调的保守起点，不是最优理论参数，也不能替代宿主账单限制。

失败记忆采用明确记录与检索，而不是把所有失败聊天拼进新 prompt。`packet` 有界并拒绝静默截断数学命题；检查点保留状态摘要、阻塞项与下一步。预算耗尽时允许诚实暂停，不让 Stop hook 因“未证明”无限重开。

**对 CoMath 的后续优化建议**：根据单步预期价值而非角色轮次分配预算；优先解锁依赖链最长的引理，或做最便宜且能排除一整条路线的测试。记录每次续跑有什么新材料/新策略，而不只是增加 token。实际 token、wall time、费用限额应由宿主计量，不能仅靠 prompt 自律。

## 4. 引理接口比完整证明历史更适合作为共享上下文

单个研究里最有价值的缓存通常不是一段模型“思考”，而是一个已经核对的可调用引理接口。建议后续引理节点至少保存：固定假设、精确结论、定义版本、依赖列表、证据类型、来源、当前状态、接口哈希和证明体哈希。

**接口变化和证明体变化应分开**。只改一个证明实现但不改接口时，可局部重验节点并保留其他路线的工作；改变假设、域或结论，则需要让依赖闭包失效。这能够比“全项目每次重来”更省力，但最终发布仍需对整合目标重新检查。缓存只能加快开发，不得替代最终有效性判断。

v9 目前采用保守实现：整份 spec 变更让旧任务失去当前权威，任务失效会取消其后继并开启问题；产物哈希变化会阻止使用。**尚未实现 Lean 语义级接口哈希或自动找出自由文本中的全部数学依赖**，关联证据需要 coordinator 显式撤回。不要把保守全局失效宣传为精确增量构建系统。

建议将开发快速回路与发布慢回路分开：开发可用已审缓存、局部编译和检索；发布则验证锁定环境、最终目标、所需依赖与审阅快照。生命周期 hook 不应充当每条工具命令之后的全库编译器。

## 5. 四种判断分开，避免一盏绿色灯吞掉所有不确定性

至少区分：**形式正确性、与原问题的语义一致性、新颖性、实际人机贡献/自主性**。证明了一个精确 Lean 类型，不自动说明形式化忠实于原意；忠实的正确证明，也可能只是已有定理的特例；完成一次流程门禁，更不是上述判断全都通过。

v9 把 candidate、experiment、refutation、integration、文献材料与 runner 产生的 `lean_replay` 分别登记。公共 evidence-add 不能直接导入一个“Lean 成功”日志充当回放。research 路径最终用 `reviewed_research`，formal 路径最多用 `reviewed_formal_local`，名称中保留范围，不叫普遍 certified。

六道门禁累计检查，反对意见不因多数 agent 支持而被覆盖。形式回放失败或证据变旧会阻断正式放行。人工复核必须针对当前 snapshot，新增材料或问题使旧签核不能无限复用。不过 `checked:true`、reviewer 字符串和 human-ack 都只是本地声明/结构，控制器无法判断人是否真读过论文，也不能证明终端前是谁。

**语义审查建议**：formalizer 先给假设/量词/符号对照，再让一个未见原始自然语言目标的独立上下文只看形式命题并反译。人工比较二者，重点看是否改了量词顺序、加入强假设、遗漏非退化条件或把需要研究的情形排除成空真。例如代数题应特别核对系数域、参数例外、可逆性与乘法次序；这些是检查项，不是模型投票项。

v9 提供过滤后的盲审 packet，但没有宿主访问隔离。真正盲审必须让宿主限制可读内容；同一会话换一个角色名字不构成独立审查。

## 6. 角色优化：九种能力，按需组合，而不是九人开会

公共角色契约已经全部重写并生成两套宿主材料。关键调整是用产出和边界定义角色，而不是“你是某某级别数学家”的人格描述。

formalizer 对目标负责，strategist 对路线/引理接口负责，librarian 对可查证来源负责，prover 对一个固定任务负责，experimenter 区分精确计算与数值/有限搜索，refuter 对反对证据负责，integrator 对规范成果唯一写入负责，auditor 对检查范围和独立性负责，coordinator 对调度、预算和下一动作负责。

默认只开瓶颈需要的 1–2 个 specialist。两条互不依赖的证明路线可以并行，同一文件的紧耦合集成不宜由多个 worker 同时改。读写 worker 在独立 attempt 目录产出 patch；只读角色返回材料，由 coordinator 登记。运行时不能让“auditor”名字自动获得人工权限。没有真实子代理工具时允许顺序检查，但日志必须如实标注。

对两个系统建议保持一个公共角色源文件和宿主差异层。v9 已提供生成器与一致性测试；CoMath 草稿还需按其真实注册表/工具合约人工映射，本包没有向未取得的 Pi extension 自动打补丁。详情见 COMATH-PROMPTS.md。

## 7. Codex 原生 hooks：轻量辅助，不重新制造一个 agent 框架

当前官方文档提供项目级 `.codex/hooks.json`，多来源 hooks 会合并并要求信任审阅；技能与 agent 有各自的原生发现目录。[S10, S11] 本包按原生 command handler 实现，不把旧 notify 回调当成通用 hooks，不虚构异步/prompt hook 能力。

SessionStart/SubagentStart 给有界状态提示；PreToolUse 对直接写控制器状态、明显自签核等有限模式做拒绝；PostToolUse 记录哈希元数据而非原始命令和输出；压缩与停止保存检查点。中性 PreToolUse 返回空对象，不主动授予工具权限。Stop 允许未解决问题停止，只在检查点失败时最多请求一次修复。

这不是全面工具沙箱：shell 多种表达方式、持久会话、宿主原生工具和同用户进程都限制了中介范围。人工确认、网络/文件权限与模型计费仍是宿主职责。安装器不修改这些设置，也不自动信任自己。

安装器支持已有 hooks 合并、同 matcher 中第三方 handler 保留、备份回滚、重复安装不改写同内容。Windows command 分支经过静态生成检查，但没有真实 Windows/Codex 执行结果。没做额外 marketplace 插件，因为这里原生 skill + hooks + agents 足够；重复插件装载反而可能让 hooks 双跑。

本环境四类 hook 的 5 次抽样中位数为约 0.66–0.72 秒，详见 benchmark-local.json。样本很小，p95 实际接近该组最大值，不能当服务等级承诺。一条同时触发 Pre/Post 的工具调用会付出两次开销；在高频工作里，这个成本不应忽视。可在实际宿主缩小 PostToolUse 匹配范围，或在后续复用已存在的 daemon 事件通道，避免为纯日志另设常驻大框架。未经同题对照，不能说研究速度已经提升多少。

## 8. 非 Pi 的等价性：优先复用内核，保留真正便携档

CoMath 既然已经公开描述直接 HTTP / in-process 入口，“不用 Pi”不必等于“另写一套证明权威”。[S01] 最完整的后续架构应是非 Pi 的薄宿主适配原 `comathd`，复用正式状态、证据 schema 和 host-only 合约。

本包实现另一个有明确用途的档位：Python 标准库、无需常驻服务、由同一研究者信任的本地工作区。它可以统一任务、记录、门禁和角色规范，但不宣称拥有 CoMath 服务的权限边界。两个档位必须给最终结果标注 trust profile；跨档结果导入先降为候选，不能搬一个成功字符串就升级认证。

本次没有取到 daemon 鉴权和真实 schemas，因此没有写一个猜参数、猜凭据的 HTTP 桥。此项是“尚未实现”，不是隐藏在安装选项背后的已完成能力。PARITY.md 给出逐项矩阵。

## 9. 新 Lean 适配器的有效范围

可定位的新增实现：`skill/runtime_v9/runner.py` 的 `lock_errors`、`verify`、`parse_axioms`、`verify_current_receipt`。它要求受支持的固定工具链和依赖清单，排除原 `.lake` 后创建新工作目录；通过随机审计 theorem 检查目标项具有已锁定的精确预期类型，读取该 theorem 的公理依赖，限定公理集合。

凭据绑定原始源码/配置、保留工作树、依赖源、工具链二进制、编译产物、审计文件、日志和验证器实现指纹。新失败不能被旧成功掩盖。静态禁用 sorry/admit/新增公理等是保守前置检查，既可能拒绝需要人工扩展的合法 metaprogramming，也不应冒充完整 Lean 解析或 kernel。

**没有真实 Lean 执行结果。** 本地通过的是适配器逻辑及 mock 流程，另留显式 opt-in 的真实 smoke test。专用 lean-demo 的 v4.19.0 是固定测试输入，不表示最新版本或你项目的推荐版本。

新目录不是安全沙箱；Lake 和依赖代码可以执行用户权限下的操作，也可能下载预编译缓存。本包不声称所有传递依赖都从源重编译，不签发完整 hermetic replay 证书。正式使用前应审查构建代码，在受控环境里运行并测试实际 mathlib 规模、依赖格式及日志行为。

## 11. 怎样验证“更高研究效率”而不是“更多 agent 活动”

建议挑选四类已知答案但对 agent 隐藏的任务：已有定理重用、需发现隐藏假设的反例任务、跨会话中断恢复、含多个依赖引理的小型形式化。保留单 agent 原始流程、当前 CoMath 和新流程三组，在模型/预算/工具链相同条件下做配对重复；对实际开放课题则按阶段义务记录，不拿最终未解决与否简单打分。

指标应是首次可复现引理所需时间、错误放行率、恢复后重复劳动、每个有效研究义务的成本、人工纠错时间、失败路线重复率和引文可核查率。不要把一次 `lake build` 成功、对话长度、完成任务数或 agent 个数当成数学质量。

最重要的发布门槛是**错误不能被错误标为通过**，其后才比较吞吐量。真实 Codex/Windows/Lean smoke、完整旧仓库回归和 CoMath 契约验收均应列为 RC 转稳定版前的未决项。当前结果详见 TEST-REPORT.md，不隐藏跳过测试。
